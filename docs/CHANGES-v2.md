# ML-патчер: согласованность решений и достоверность обратной связи

Дата: 25 сентября 2026. Версия планировщика: `planner/v2`.

Это изменения исходного кода, а не обученная модель и не подтверждённое повышение успешности патчей на реальных APK. Основная цель — исключить противоречивые решения, проверять кандидатов до выбора победителя и не загрязнять будущую обучающую выборку вымышленными результатами.

## Исходник и состав поставки

Оба загруженных файла с расширением `.md` оказались одинаковыми ZIP-архивами. SHA-256 исходного архива:

````text
e712f1fa71668d877354bd5eb2668250cdd9a11c62260c834c7b52fa8b813791
````

`Mega-Analyzer-original.zip` — исходный архив с корректным расширением. `Mega-Analyzer-ML-improved.zip` — полный проект с изменениями, этим `CHANGES.md` и копией `ML-patcher-improvements.patch` в корне. Отдельный `.patch` содержит только изменения относительно присланного исходника, включая тесты и документацию; сам себя патч не включает. Применять патч поверх уже обновлённого ZIP не нужно.

## Что исправлено

| Участок | Найденная проблема | Изменение |
| --- | --- | --- |
| Конфликтующие сигналы | `BuildChangeRequest` возвращал ошибку, но `GenerateBest` её игнорировал; `GenerateWithMode` переходил в legacy-генератор. Пустое `Desired` позволяло снова угадывать намерение. | Общий `validateChangeRequest`; конфликт блокирует оценку, генерацию и проверку. `GenerateBest` возвращает ошибку. `GenerateWithMode` и legacy-вход `Generate` не создают патч при конфликте. |
| Несогласованные селекторы | `SelectStrategyWithSignals` и `RankStrategies` брали первый подходящий сигнал и обходили request-aware требования CFG/DFG. | Оба публичных входа используют `BuildChangeRequest` и общую request-aware ранжировку. Стабильная сортировка при равном балле сохранена. |
| Поздний структурный отказ | Планировщик выполнял `ValidateStrict`, а проверки сохранения тела из `buildArtifact` запускались уже после выбора. | Для типов, охваченных существующим `requiresStructurePreservation`, `preflightBodyStructure` выполняется внутри цикла кандидатов. После ошибки рассматривается следующий кандидат. |
| Необъяснимые отказы | Неприменимые стратегии исчезали из плана; ошибки генератора и валидатора терялись. | `PlannedPatch.Candidates` сохраняет неприменимые стратегии, `DropReason`, `Assessment.Reasons`, ошибку генерации и результат валидации. `RejectionReason` объясняет отсутствие итогового патча. Публичная ранжировка по-прежнему возвращает только применимые стратегии. |
| Пустые и неизменённые результаты | Пробельный результат и точная копия исходника могли претендовать на выбор. | Пробельный патч отклоняется; совпадение с исходником после нормализации CRLF/концевых переводов строк получает `no_change`. Это текстовая, не полная семантическая проверка эквивалентности. |
| Идентичность цели | Проверялось главным образом имя метода; перегрузка и фактический заголовок тела могли не совпадать с запросом. | Проверяются известные путь и дескриптор, а также имя/дескриптор `.method` в сгенерированном теле. Дескриптор запроса берётся из полной сигнатуры либо заголовка. Выбранный результат получает метаданные целевого метода. |
| Недостоверный успех сборки | `OutcomeForPlannedPatch` выставлял `Build=pass` после статической проверки Smali. APK не собирался. | Добавлен независимый `StaticValidation`. Сборка, целевой результат и регрессии остаются `unverified`, пока не получены реальные результаты соответствующих проверок. |
| Потеря поздних результатов | Первое событие с неизвестным исходом блокировало последующую отправку результата как дубликат. | Новые факты дополняют существующее событие без увеличения `Outcomes`. Повторы и устаревшие неизвестные состояния не стирают подтверждённые факты. Противоречащие `pass/fail` отклоняются атомарно. |
| Смешение версий и коллизии | Ключ не учитывал версию генератора/модели и склеивал поля через `|`. | Ключ строится из JSON-кортежа с версиями и SHA-256. Добавлен `GetStrategyStatsForVersion`; старый `GetStrategyStats` остаётся общей сводкой по всем версиям. |
| Качество входных событий | Принимались неполные идентификаторы и произвольные статусы; запись меняла Timestamp объекта вызывающего кода. | Проверяются обязательные поля, SHA-256 и enum статусов. Пустые статусы нормализуются в `unverified`. Обрабатывается копия события; изменения и счётчики защищены одним mutex. |

В идентификатор исхода включаются файл и дескриптор метода. Хеш исходника берётся из полного тела запроса, если оно доступно, а не из сокращённого текста для отображения. Статистика отдельно учитывает статическую проверку, обнаружение, сборку, цель, регрессии, дополнения, дубликаты и конфликты.

## Изменение поведения API

`GenerateWithMode` теперь возвращает `nil`, если план отклонён или ни один кандидат не прошёл проверки. Раньше в этой ситуации мог возвращаться legacy-шаблон. Это намеренное изменение: отсутствие доказанного кандидата не является разрешением создавать другую правку. Вызывающему коду нужно обрабатывать `nil` как отсутствие пригодного предложения. Для диагностики используйте `BuildChangeRequest` → `PlanPatch`.

`SelectStrategyWithSignals` возвращает стратегию, но не переносит запрос в последующий ручной вызов `strategy.Generate`. Для сохранения намерения на всём пути используйте `GenerateBest` либо `PlanPatch`, а не пару `Select...` → `Generate`.

`RecordStrategyOutcome` возвращает `true` как для нового события, так и для дополнения существующего новыми фактами. Повтор, конфликт и некорректный ввод возвращают `false`. `Outcomes` при дополнении не увеличивается; различия отражаются в `Updates`, `Duplicates`, `Conflicts`. Пустой статус нормализуется в `unverified`; `not_run` не считается ошибкой или успехом. Известный `pass` не заменяется неизвестным статусом. Противоречащие подтверждённые факты требуют отдельного разбора, а не правила «последняя запись победила».

Новые события должны содержать непустые `StrategyID`, `GeneratorVersion`, `TargetID`, корректные SHA-256 `SourceHash`/`PatchHash`. `MetaModelVersion` может быть пустым для непомеченной версии модели. Для сравнения поколений используйте `GetStrategyStatsForVersion`; общая сводка не является однородной обучающей выборкой. Старые события `planner/v1` с `Build=pass` нельзя считать доказательством реальной сборки без внешнего подтверждения.

## Тесты и реально выполненная проверка

Добавлены **13 тестовых функций** в `planner_safety_regression_test.go` и `strategy_outcome_safety_test.go`, с дополнительными табличными случаями. Они проверяют отказ при конфликте в обоих порядках сигналов, переход к следующему кандидату после структурной ошибки, сохранение диагностики, no-op, идентичность цели, отсутствие legacy-обхода, раздельный учёт статической проверки/сборки, дополнение событий, атомарность конфликтов, версии, коллизии разделителя, недопустимые данные, нормализацию и 32 параллельные повторные отправки.

Существующий `TestChangeRequestConflict` изменён: ожидание legacy-патча заменено ожиданием отказа. Остальные старые тесты не ослаблялись ради новых ограничений.

| Проверка | Статус |
| --- | --- |
| Формат исходных вложений и их SHA-256 | Проверено; оба вложения одинаковы |
| `git -c core.whitespace=cr-at-eol diff --check` | Выполнено без ошибок; CRLF исходных изменённых файлов сохранены |
| Баланс разделителей, строк и комментариев в изменённых Go-файлах | Проверено скриптом; **не является Go-парсером или компиляцией** |
| Применение `.patch` к чистой распаковке и побайтовое сравнение результата | Проверено при упаковке |
| Целостность выходных ZIP | Проверена при упаковке |
| `go test`, `go test -race`, `go vet`, `gofmt` | **Не выполнены**: Go/gofmt отсутствуют в the Computer |
| APK rebuild, ART/эмулятор, целевые сценарии | **Не выполнялись** |
| Обучение новой модели и сравнительный бенчмарк качества | **Не выполнялись** |

Попытка запуска целевого `go test` завершилась кодом 127: `go: command not found`. В `go.mod` указан `go 1.27.1`; файл не менялся ради обхода ограничения. Для the Computer нет разрешённых внешних доменов; альтернативный инструмент загрузки отказал для MIME-типов архивов Go. Утверждения о компиляции, зелёном тестовом наборе или росте точности отсутствуют. До использования этих изменений нужен Go-прогон. Старые проверки, требующие обязательного fallback-патча, могут потребовать пересмотра в соответствии с новым fail-closed контрактом — не следует отключать новые ограничения лишь для восстановления прежнего поведения.

## Применение к исходной версии

Распакуйте **исходный** ZIP и выполните команды из корня проекта. Если используете готовый обновлённый ZIP, этот шаг пропустите.

````sh
git -c core.whitespace=cr-at-eol apply --check /path/to/ML-patcher-improvements.patch
git -c core.whitespace=cr-at-eol apply /path/to/ML-patcher-improvements.patch
````

При установленном совместимом Go выполните:

````sh
go version
go test ./pkg/ml -run '^(TestPlannerSafety|TestOutcomeSafety|TestChangeRequestConflict|TestStrategyOutcomeDedup)' -count=1
go test -race ./pkg/ml -run '^TestOutcomeSafety' -count=1
go test ./pkg/ml/... -count=1
go vet ./pkg/ml/...
````

Проверьте форматирование изменённых `.go` штатным `gofmt`. Для полной интеграционной проверки затем нужен `go test ./...` и отдельная сборка/прогон собственных тестовых APK. Не считайте успешный внутренний Smali-валидатор эквивалентом сборки и выполнения на ART.

## Что улучшать дальше

Следующий полезный шаг — не увеличение фиксированных приоритетов и не добавление множества паттернов. Нужен размеченный корпус собственных сценариев с разделением train/calibration/test по приложениям, а не по методам одного APK. Оценивать стоит precision@K, долю отказов, фактическую сборку, достижение целевого результата и регрессии. Версионные исходы в этом изменении дают более достоверную основу для такого сравнения, но обучаемый ранжировщик пока не добавлен.

Остаются отдельные задачи: сквозная гарантия `PreserveSideEffects`; типизированный учёт частичности вместо анализа `Description`; использование выбранной инструкции всеми стратегиями; проверка потока данных на каждом пути; сохранение событий стратегий между запусками и связь с идентичностью приложения/эксперимента. Текущий структурный префлайт остаётся эвристическим и применяется к существующему набору типов `requiresStructurePreservation`, а не доказывает семантическую корректность всех стратегий. Legacy-режим без явно выбранного режима сохранён, кроме блокировки конфликтующих сигналов.
