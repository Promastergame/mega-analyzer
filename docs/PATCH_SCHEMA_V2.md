# Patch Bridge Schema 2.0

[Русский](PATCH_SCHEMA_V2.ru.md)

Schema 2.0 is the compatibility contract between the Go analyzer/generator and the Zig APK Editor. Existing schema 1.x fields remain valid; every new field is optional for old consumers.

## Identity

Each patch has `patch_id`, derived from the normalized file path, exact method name, and Dalvik method descriptor. This prevents overloaded methods such as `check(I)Z` and `check(Ljava/lang/String;)Z` from colliding. `method_signature` remains the human-readable/exact matching anchor.

## Safety and drift

`apply_safe` is authoritative for automatic IDE application. `apply_safety_level` and `safety_reasons` explain manual-review decisions. `original_hash` and `patched_hash` describe canonical LF-normalized method bodies. The editor reports source drift rather than replacing an unrecognized method.

## Minimal apply plan

The flattened block fields are intended for consumers that do not parse nested artifacts:

| Field | Meaning |
|---|---|
| `block_start_line`, `block_end_line` | Analyzer-relative changed window |
| `block_original_code` | Exact original changed block |
| `block_patched_code` | Replacement block |
| `block_original_hash` | Canonical source block hash |
| `block_patched_hash` | Canonical destination block hash |

The Zig editor first attempts exact whole-method matching. If unrelated source drift occurred outside the changed window, it can safely apply the unique block replacement. Ambiguous or missing blocks are rejected.

## Idempotency and revert

Applying an already patched method succeeds without rewriting it. Revert performs the inverse method/block replacement and never restores the entire `.original` snapshot. The snapshot remains a manual disaster-recovery copy only.

## Editor states

A patch preflight produces one of: `ready_method`, `ready_block`, `already_applied`, `blocked`, or `source_drift`. Batch apply records separate counters for these outcomes and keeps accepted queue state in `patches-addon.json`; analyzer-owned `patches.json` is not modified.

## ML candidate review boundary

The Go ML package exposes an intermediate `PatchCandidate` through
`BuildPatchCandidate`. This object is a recommendation, not an apply command.
It contains a stable candidate ID, source hash, score, confidence, risk,
structured evidence, and a `ready`/`review`/`blocked` status. Consumers must
run `PreflightPatchCandidate` and then use the schema 2.0 patch preflight before
calling an apply operation.

The candidate preflight rejects non-application code, unsafe method structure,
missing strategies, and return-type mismatches. Generated Smali still requires
`SmaliValidator` validation; a recommendation status must never be treated as
proof that the generated APK will build or launch.

## Strategy and SDK planning

Strategy selection now has an assessment layer in addition to the legacy
`CanApply` contract. The layer classifies method roles, applies return-type and
unsafe-control-flow gates, and allows a strategy to expose `StrategyMetadata`
and an explainable `StrategyAssessment`. Existing strategies remain compatible,
but whole-body strategies are denied for exception, switch, and coroutine
methods unless a future strategy explicitly declares control-flow preservation.

SDK inventory is exposed through `DetectSDKInventory`. Unlike the legacy
`DetectSDK` list, each result includes SDK family, version hint, confidence,
evidence, and ownership (`sdk_library` or `app_wrapper`). SDK-library matches
are audit-only by policy; an app wrapper is still review-only until a concrete
call/data-flow decision point has been proven.

Synthetic return generation is centralized in `BuildTypedReturnPatch` and the
shared `patch_smali_builder.go` backend. Legacy `SmartPatcher` artifacts now
use this typed path and are strict-validated before they can be writable.
Unsupported operations such as placeholder URL replacement are blocked instead
of producing a fake method body. Body-aware constant/call-site operations must
be generated by `PatchGenerator`, where the original method context is
available.

`SmartPatch.BindSource` must be called before a SmartPatch artifact is
considered writable. A signature-only SmartPatch is preview/diagnostic data;
it has no authoritative source hash and is blocked by `ToPatchArtifact`.

The built-in return, constant, condition, partial, NOP, numeric, and price
strategies expose metadata to the selector. This metadata records supported
method roles and return descriptors, whether CFG/DFG evidence is required, and
whether the strategy is high risk. The selector still supports legacy custom
strategies, but they do not receive metadata-specific ranking until they opt in
through `StrategyDescriber`.

Candidates also carry an explicit `ReviewPolicy`, server-dependency
classification, and defensive recommendations. Current scopes are `audit`,
`defensive`, and `test_fixture`; all are review-required and diagnostic-only.
The policy contract intentionally has no automatic apply path. SDK matches can
also report wrapper methods, native/JNI signals, and dependency hints so the
report covers app-owned integration code instead of only SDK internals.

Artifacts for surgical patch types (`nop`, `const_replace`, `return_zero`, and
`return_max_int`) now receive a structural preflight. It checks that labels
remain present, every branch target still resolves, and try/catch region counts
are unchanged. A failed structural preflight makes the artifact non-writable,
even when lexical Smali validation succeeds.

The structural preflight also builds the existing internal CFG for the
original and destination method and compares basic-block count, edge shape,
and unreachable-node count. A surgical artifact is writable only when this
graph-level comparison remains stable; a constant-only edit is accepted while
an edge-changing edit is blocked.

The same gate performs a conservative use-def pass: `move-result*` must follow
an invoke, and v-registers used by the destination method must have a visible
definition. This is not a replacement for ART verification, but it catches the
common surgical failure where an invoke is removed and its result consumer is
left behind.

The preflight also compares DFG value roles feeding return sites and branch
predicates. It permits the intended `return` constant override, but blocks a
patch that silently replaces an invoke/field-derived branch input with an
unrelated value. This remains conservative and is an additional gate, not a
substitute for ART execution or APK rebuild verification.

CFG/DFG memory is bounded by `PredictorConfig.CFGCacheCapacity` and
`CFGCacheTTL` (defaults: 128 graphs and 5 minutes). `CFGCacheStats` exposes
approximate retained memory, and `ClearCFGCache` releases graphs between APK
runs. Structural preflight builds temporary graphs and does not add them to
the predictor cache.
