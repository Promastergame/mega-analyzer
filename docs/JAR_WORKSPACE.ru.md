# JAR bytecode + «Мой компьютер» в --web

## Статус поставки

Это исходники первого этапа улучшений, а не проверенный релиз или готовый EXE. В the Computer отсутствуют Go и gofmt; установка пакетов недоступна. **Компиляция, Go-тесты, go vet, race detector и fuzzing не запускались.** Перед использованием необходимо выполнить команды ниже. Существующий `go.mod` с `go 1.27.1` не изменён.

Выполнены проверки синтаксиса двух JS-файлов через Node, smoke-тест логики проводника на минимальной модели DOM, `bash -n` нового скрипта, проверка ссылок UI на HTML-элементы, уникальности HTML id и лексических разделителей изменённых Go-файлов. Это не заменяет Go-компиляцию, реальные HTTP-тесты или проверку в браузере. Протокол: `docs/review-jar-workspace/checks.json`.

Добавлено **25 Go-тестовых функций и один fuzz-target**. Исходный архив не запускался; Java-классы и подозрительные образцы не исполнялись. Внешние базы CVE не загружались, измерений точности/скорости нет.

## Что изменилось в JAR-анализе

Ранее основной детектор опасных Java API работал с символическими ссылками constant pool. Теперь `.class` дополнительно разбирается по границам настоящих JVM-инструкций. Обрабатываются `invokevirtual`, `invokespecial`, `invokestatic`, `invokeinterface`, `invokedynamic`, переменные размеры `tableswitch`/`lookupswitch` и `wide`. Проверяются обрезанные инструкции, зарезервированные opcodes, ссылки invoke в constant pool, padding и диапазоны switch, а также попадание branch targets на границы инструкций.

Наличие invoke — **доказательство инструкции в файле, не её достижимости или выполнения**. Для sink-находки сохраняются первый подходящий call site, caller method, descriptor, offset, opcode и количество найденных call sites. Перегрузки сопоставляются по descriptor. Неиспользуемая ссылка остаётся `constant_pool_reference`, а не превращается в выдуманный вызов. Полный call graph в этом этапе не строится.

`BootstrapMethods` проверяется и связывается с `invokedynamic` в разобранном `ClassFile`. Bootstrap method не объявляется целевой функцией лямбды. Полное разрешение lambda implementation handles, StringConcatFactory и динамического dispatch ещё не реализовано; в пользовательские sink-находки сейчас поднимаются прямые invoke, а не предположения о поведении лямбд.

Добавлена проверка **точных простых TLS-заглушек**: публичный нестатический `X509TrustManager.checkServerTrusted/checkClientTrusted` с правильным descriptor и телом только `return`, а также `HostnameVerifier.verify` с телом ровно `iconst_1; ireturn`. Это более сильное доказательство, чем один факт реализации интерфейса. Но установка данного TLS-объекта приложением не доказана. Более сложные варианты, наследование и flow-sensitive анализ пока не покрываются.

Каталог API дополнен `MethodHandles$Lookup.defineClass/defineHiddenClass` и `Runtime.load/loadLibrary`. Сам по себе такой API не означает вредоносность. Анализ строк криптоалгоритмов и существующие dependency-эвристики не превращены в dataflow-анализ.

Структурированные доказательства теперь не теряются при преобразовании в общий отчёт: `analysis.json` получает `artifact_findings[].jvm_evidence`. В веб-таблицу включены артефактные находки; пояснение вызова доступно в tooltip строки, полный набор полей — в JSON. Пример структуры доказательства:

````json
{
  "evidence_type": "bytecode_invocation",
  "method_name": "run",
  "metadata": {
    "evidence_kind": "bytecode_invocation",
    "bytecode_offset": "12",
    "opcode": "invokevirtual",
    "execution_proven": "false",
    "reachability_proven": "false"
  }
}
````

В памяти удерживается не более 4096 call sites на класс. Инструкции после лимита продолжают декодироваться, но доказательства могут быть неполными: общий JAR Report получает inspection issue и `complete: false`, основной конвейер выводит предупреждение. Счётчик удержанных вызовов тогда является нижней границей. Это не полноценный JVM verifier: stack types, stack maps, полная корректность descriptors, exception-handler instruction boundaries и достижимость не проверяются.

Изменения sink-находок относятся к общему JAR-анализу / Full Static Analysis. Minecraft-режим использует общий парсер классов и получает более строгий разбор bytecode, но сохраняет собственный каталог индикаторов; общий TLS/SAST-анализ автоматически в него не переносился.

## «Мой компьютер» в --web

В боковом меню добавлена кнопка **«Мой компьютер · Results»**. Она открывает файловый кабинет поверх текущего интерфейса, не переключая режим и не останавливая активный анализ. Есть папки, навигационная строка пути, создание папок, фильтр загруженных объектов, обновление, постраничная загрузка, статусы сканов, просмотр текстов/JSON/HTML и скачивание отдельных файлов.

Чтобы сгруппировать проверки, создай папку, открой её и нажми **«Сохранять сюда»**. Следующий анализ создаст внутри новую папку запуска. Можно также указать относительный путь в поле `Workspace folder`, например `Projects/MyMod`. Имя результата — отображаемая подпись, а не путь на диске.

Каждый запуск получает уникальный криптографически случайный ID и отдельную папку, даже если имя результата повторяется. Пример:

````text
workspace/
  Scans/
    2026-09-20_140000_<random-id>/
      .scan.json            служебная запись, скрыта в проводнике
      scan.log              хвост журнала после завершения
      results/
        analysis.json       если этот режим его создаёт
        REPORT.html         если этот режим его создаёт
        ...                 остальные артефакты режима
  Projects/
    MyMod/
      ...
````

Метаданные создаются до запуска анализатора и заменяются через временный файл + rename после завершения. Восстанавливаемый статус и список файлов читаются с диска: перезапуск `--web` и удаление старой задачи из памяти не убирают результаты из кабинета. Статусы: `running`, `completed`, `failed`, `stopped`, `interrupted`. Последний означает, что запись была оставлена незавершённой другим запуском сервера; это не определение состояния оставшегося дочернего процесса.

Журнал сохраняется при штатном завершении или обработанной ошибке; сохраняется хвост до 8 MiB с отметкой об обрезании. При жёстком завершении процесса промежуточный журнал из памяти может быть потерян. Уже записанные движком артефакты остаются. Старые SSE/job URL после перезапуска не восстанавливаются: историю открывай через «Мой компьютер». Одновременное использование одного workspace несколькими серверными процессами не поддерживается как полноценный multi-instance режим.

## Где лежат результаты

По умолчанию используется `os.UserConfigDir()/Mega-Analyzer/workspace`: обычно `%AppData%\Mega-Analyzer\workspace` на Windows и `~/.config/Mega-Analyzer/workspace` на Linux. Пользовательский каталог выбран, чтобы запись работала и при read-only расположении бинарника.

Корень можно задать **при запуске сервера**, не из браузерного файлового API:

````bash
MEGA_ANALYZER_WORKSPACE="$HOME/mega-results" ./analyzer --web
````

````powershell
$env:MEGA_ANALYZER_WORKSPACE = 'D:\MegaResults'
.\analyzer.exe --web
````

Для встраивания также есть `web.Options.Workspace`. CLI-флаг `--web-workspace` в этом этапе не добавлялся. Для просмотра одного и того же хранилища после перезапуска сохраняй значение переменной и запускай сервер под тем же пользователем. При переходе на другой OS-account, включая admin, каталог по умолчанию может измениться.

**Изменение совместимости:** поле `output` в `/api/scan` теперь принимает только относительный каталог внутри workspace. Произвольный абсолютный путь из веб-формы отклоняется. Обычный CLI `-output` вне веб-формы не изменён. Старые результаты в `analysis_output` автоматически не импортируются; при необходимости копируй доверенные отчёты в отдельную папку workspace при остановленном сервере — файлы будут видны, но без исторических scan-метаданных.

## Границы безопасности и ограничения

Файловые операции нового API используют `os.Root`; дополнительно отклоняются `..`, абсолютные и Windows drive-пути, скрытые компоненты, symlink entries и специальные файлы. Нельзя создать новый скан внутри папки старого скана. Новые endpoints проходят существующие token/origin/Host guards; write-операция создания папки требует POST. Дополнительные CLI-флаги веб-формы теперь проверяются по allowlist, чтобы нельзя было подменить `-output`, `-t`, режим или очистить каталог через `-clean-output`.

Предпросмотр ограничен текстовыми расширениями и 2 MiB. HTML отображается в iframe с пустым `sandbox`: без scripts, доступа к родительскому окну и внешних ресурсов; интерактивные элементы HTML-отчёта могут не работать. Скачивание выдаётся как attachment, а не активная страница. JSON, имена файлов и статусы вставляются как текст. Скачанные отчёты всё равно следует считать недоверенным содержимым.

Это **не VM, не изоляция дочернего анализатора и не новая гарантия безопасности старых API проекта**. Динамический анализ сохраняет прежние риски выполнения на выбранном хосте/устройстве. Корень workspace должен быть доверенным каталогом, не доступным на запись посторонним пользователям. Не размещай там системные секреты и не открывай веб-сервер в интернет без отдельной защиты.

В этой версии нет терминала, запуска JAR из проводника, удаления/перемещения сканов, корзины, ZIP-экспорта папки, фонового полнотекстового поиска, автоматической миграции, пользователей/ролей или дисковой квоты. Результаты автоматически не удаляются; следи за свободным местом и делай резервные копии. Удаление пока только вручную на диске при остановленном сервере.

## Проверка и сборка

На машине с подходящим Go toolchain из корня проекта:

````bash
bash scripts/validate-jar-workspace.sh
RACE=1 FUZZ=1 INTEGRATION=1 bash scripts/validate-jar-workspace.sh
go build -trimpath -o analyzer ./pkg/cmd/analyzer
./analyzer --web
````

Скрипт форматирует только изменённые Go-файлы через gofmt, запускает целевые тесты и vet. Race требует поддерживаемой платформы и C toolchain; интеграционные тесты могут требовать компоненты исходного проекта. Скрипт ничего не устанавливает и не запускает анализируемый JAR.

Без Bash на Windows выполни `gofmt -w` для изменённых Go-файлов, затем:

````powershell
go test -count=1 ./pkg/internal/jarloader ./pkg/internal/types ./pkg/cmd/analyzer/web
go vet ./pkg/internal/jarloader ./pkg/internal/types ./pkg/cmd/analyzer/web
go test -count=1 ./pkg/internal/apkloader ./pkg/cmd/analyzer ./pkg/minecraft
go build -trimpath -o analyzer.exe ./pkg/cmd/analyzer
.\analyzer.exe --web
````

Проверка JS без зависимостей:

````bash
node --check pkg/cmd/analyzer/web/assets/app.js
node --check pkg/cmd/analyzer/web/assets/workspace.js
node scripts/test-workspace-ui.cjs
````

После сборки вручную проверь в браузере: папку с кириллицей, два одноимённых скана, перезапуск и открытие старого JSON, отказ на абсолютный output, HTML с тестовым script без его исполнения, большой файл с отказом предпросмотра и рабочим скачиванием, просмотр результатов активного анализа без его остановки. На Windows отдельно проверь замену `.scan.json` при завершении и доступность выбранного каталога.

## Куда усиливать JAR дальше

Самый полезный следующий шаг — не ещё сотня regex и не переписывание всего на Rust, а **поток данных поверх JVM-инструкций**. Нужны IR стека/locals, CFG, summaries методов, точки входа из manifest/Fabric/Quilt/Forge/Spring/servlet и цепочки source → transformations → sink. Так можно отличать безопасный фиксированный вызов Runtime.exec от команды, построенной из недоверенного ввода, и реальную передачу секретов от соседства строк и сетевого API. Отдельно потребуются aliasing и проверка того, какой именно XML/TLS-объект был настроен.

Следующий слой — корректная модель загрузки: Multi-Release JAR под выбранную Java, shadowed classes, библиотеки отдельно от прикладного кода, lambda/metafactory/concat bootstraps и ограничения разрешения reflection. Для обфускации лучше ограниченный статический evaluator распространённых string decoders с бюджетами, а не запуск чужих классов.

Для supply-chain нужны SBOM с Maven GAV/PURL, обновляемая advisory-база с датой и происхождением, корректные version ranges/backports и независимая проверка целостности JAR signatures. Наличие подписи не равно доверию к издателю; имя файла не является подтверждением CVE.

Качество должно подтверждаться размеченным корпусом, negative fixtures, golden reports, fuzzing, precision/recall по правилам и измерением пиков RAM/CPU на fat JAR. Только после профилирования имеет смысл переносить горячие участки ZIP/bytecode в Rust; наличие второго языка само по себе не делает анализ точнее.
