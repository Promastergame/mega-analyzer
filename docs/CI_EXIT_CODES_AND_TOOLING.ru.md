# Коды выхода для CI, композитные правила, PURL/CycloneDX, калибровка и known-set

Все возможности ниже реализованы собственным кодом Mega-Analyzer. Поведение по умолчанию не изменено.
Реальный эффект на детекты по живым APK **не измерялся** — покрыто только юнит-тестами.

## 1. Коды выхода (`-exit-codes`, `-fail-on`)

Флаг `-exit-codes` выключен по умолчанию (обратная совместимость).

| Код | Смысл |
| --- | --- |
| 0 | чисто |
| 1 | есть находки не ниже `-fail-on` (`critical` по умолчанию; `high`, `medium`, `low`) |
| 2 | есть находки на одну ступень ниже порога |
| 3 | ошибка запуска/ввода |
| 4 | анализ неполный (ошибка разбора, лимиты, ни один файл не проанализирован, прерывание, деградация правил) |

Приоритет: 1 > 4 > 2 > 0. Пропуск по размеру и неподдерживаемые файлы неполнотой не считаются.

## 2. Правила rules/v2

Старый JSON-формат работает без изменений. Новые поля правила:
`kind` (`detect`/`context`), `requires` (композиты), `unless`, `downgrade`, `confidence`, `reason`,
`suppresses`/`downgrades` (селекторы: `id`, `prefix*`, `tag:x`, `category:x`).

- `Lint()` находит неизвестные ссылки, циклы и «осиротевшие» context-правила.
- `Health()` считает пропущенные правила; при потере правил анализ помечается деградировавшим (код 4).
- Пользовательские правила: переменная `MEGA_ANALYZER_RULES_DIR` (входит в отпечаток кэша).
- Осторожно: context-правила, опирающиеся на имена классов/пакетов, подделываются злоумышленником.
  Используйте только `downgrades` (понижение), а не `suppresses` (полное скрытие), для опасных категорий.

## 3. SBOM: PURL и CycloneDX

Зависимости получают `purl` (maven / golang / generic). SPDX содержит `ExternalRef purl`,
дополнительно пишется `sbom.cdx.json` (CycloneDX 1.5, детерминированный serialNumber).

## 4. `cmd/fp-calibrate`

Подбирает порог под бюджет ложных срабатываний (по умолчанию N на 10 000 чистых образцов) по маршрутам.
Вход NDJSON `{"route","label","score"}`. Порог не бывает мягче запрошенного; для малых корпусов
`Resolvable=false`. **К живому скорингу не подключено** — нужен размеченный benign-корпус.

```
go run ./cmd/fp-calibrate -in scores.ndjson -out grid.json
go run ./cmd/fp-calibrate -grid grid.json -route general -budget 5
```

## 5. `cmd/knownset-build`

Двоичный набор «известно хорошее / известно плохое»: bloom для good (возможно ложное «да»),
точный отсортированный список для bad; bad всегда приоритетнее good; контрольная сумма sha256.
Вход NDJSON `{"sha256","purl","label":"good|bad"}`. **К пайплайну не подключено**;
подключать следует только так: bad — громкое предупреждение, good — информационная заметка, но не пропуск анализа.

```
go run ./cmd/knownset-build -in pool.ndjson -out known.set
go run ./cmd/knownset-build -check known.set -sha256 <hex>
```

## 6. `-known-set` (подключено к сканированию)

Флаг `-known-set bundle.set` включает сверку с набором — строго в безопасной схеме:

- входной файл (APK/IPA/бинарь) ищется по sha256; SBOM-зависимости — по PURL;
- `known-bad` (точный список) → находка `known_bad`, `Severity=critical`, участвует в `-exit-codes` гейте;
- `known-good` (bloom, возможен ложный «да») → заметка `known_good`, `Severity=info`, на гейт не влияет;
- анализ никогда не пропускается, находки никогда не скрываются — только добавление;
- битый/нечитаемый бандл → warning + деградация `knownset` (код 4 при `-exit-codes`), скан продолжается;
- каталог как цель по sha256 не ищется (хеш не определён), PURL-сверка SBOM работает как обычно.

```
analyzer -t app.apk -known-set known.set -exit-codes
go run ./cmd/knownset-build -in pool.ndjson -out known.set
```
