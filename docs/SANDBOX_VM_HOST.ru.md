# Отчёты на своём ПК, образец в Windows-VM

Дополнительный компьютер или облачный сервер не нужен. Анализатор работает
на основной Windows и сохраняет отчёты на её локальном диске. Образец и
`frida-server.exe` работают в отдельной Windows-VM в VMware или Hyper-V.
Название `frida-server` означает программу-агент внутри VM.

```text
Твой ПК — основная Windows
  analyzer + Python/Frida → TLS-соединение к агенту внутри VM
  analysis_output/sandbox/remote-…/
    events.jsonl          ← события записываются и Sync выполняется сразу
    sandbox_report.json   ← ключи в crypto_analysis.materials
    sandbox_report.md

  Windows-VM
    frida-server.exe → перехваты API → образец
```

Гостевая Windows не получает папку отчётов. Если она перестанет загружаться
или VM выключится, уже принятые и записанные события останутся на основной
Windows. Ключ, который не успел попасть в сборщик, восстановить этим способом
нельзя. Данные, ещё находящиеся в очереди Frida, также могут потеряться.

## 1. Подготовить VM

Этот режим **не создаёт VM, не настраивает её изоляцию и не управляет снимками**.
Он также не проверяет, что удалённый Windows-агент действительно находится в VM.

- VMware: выделенная сеть **Host-only**, без NAT и Bridged.
- Hyper-V: выделенный **Internal switch**, без NAT и общего доступа к интернету.
- У гостя не должно быть второго сетевого адаптера, доступа к локальной сети
  или маршрута в интернет. Выделенная подсеть не должна включать другие рабочие VM.
- Отключите общие папки, диски, буфер обмена, drag-and-drop, USB passthrough;
  для Hyper-V — перенаправление ресурсов Enhanced Session.
- На основной Windows блокируйте новые входящие подключения от гостевой подсети.
  Анализатор сам устанавливает исходящее соединение к агенту, входящий сервер
  на основной Windows ему не нужен. Host-only/Internal сами по себе **не блокируют**
  доступ гостя к службам хоста.
- В firewall гостя разрешите порт агента только с IP основной Windows на этом
  виртуальном адаптере. Не открывайте этот порт на обычной сети.
- На чистой гостевой системе сделайте снимок. Лимиты RAM/CPU выставляются в гипервизоре.

Граница защиты здесь — гипервизор и его настройки. Перехваты Frida не являются
защитой от выхода из VM и не дают гарантии безопасности основной Windows.
На госте не должно быть личных данных и учётных записей.

## 2. Создать профиль на основной Windows

На хосте нужны Python с пакетом `frida` и собранный анализатор. Версия Frida SDK
на хосте должна совпадать с версией `frida-server` для архитектуры гостя.

Команды выполняются из корня исходников. Пример IP ниже нужно заменить на
**IP гостевой Windows** из её `ipconfig`, а путь Python — на свой:

```powershell
go run ./pkg/cmd/sandbox-collector -init .\vm-capture -endpoint 192.168.56.10:27042 -python 'C:\Path\To\Python\python.exe'
```

Будет создана новая папка; существующая папка не перезаписывается:

| Файл | Где использовать |
| --- | --- |
| `vm-capture/host.json` | Только на основной Windows; адрес VM, токен, путь Python, массив аргументов образца `args` |
| `vm-capture/server.pem` | На основной Windows; закреплённый публичный TLS-сертификат агента |
| `vm-capture/guest/agent.pem` | В VM; сертификат и закрытый ключ агента |
| `vm-capture/guest/start-agent.ps1` | В VM; запуск агента с TLS и токеном |

Перенесите `guest/` и официальный `frida-server.exe` в чистую VM до анализа,
например через временный ISO, затем отсоедините носитель. Не создавайте для
этого постоянную общую папку. Образец тоже должен уже находиться внутри гостя.
Хостовый анализатор его не копирует и не открывает.

Профиль содержит секрет подключения. Храните его и отчёты в папке с доступом
только для своей учётной записи Windows; Unix-режим `0600` не заменяет NTFS ACL.

Внутри VM запустите агент с нужными правами:

```powershell
.\start-agent.ps1 -Agent 'C:\Lab\frida-server.exe'
```

## 3. Запустить анализ с основной Windows

```powershell
go run ./pkg/cmd/analyzer -sandbox-remote-config .\vm-capture\host.json -t 'C:\Lab\sample.exe' -sandbox-duration 60 -sandbox-output .\analysis_output
```

Здесь `C:\Lab\sample.exe` — путь **в гостевой Windows**. `-sandbox-output` —
локальная папка **основной Windows**, не сетевой диск и не папка гостя.
Аргументы программы задаются JSON-массивом `args` в `host.json`; shell на хосте
для запуска образца не используется. При недоступности VM локального fallback нет.

Отчёт и журнал находятся в `analysis_output/sandbox/remote-…/`. Точные пути
печатаются в консоль, в том числе при ошибке. Ключевые события сразу обновляют
JSON и Markdown, остальные события — примерно раз в секунду. Каждое принятое
событие сначала сохраняется с `Sync` в `events.jsonl`, затем подтверждается.

Это отдельный CLI-режим. Запуск Windows-образца через веб-кнопку на основной
Windows заблокирован. Веб-интерфейс имеет отдельный [режим VMware через Tools](VMWARE-SAFETY.ru.md)
для базового наблюдения с отключённой сетью; live-сеанс этого Frida-сборщика
к нему не подключён. Для собственных доверенных тестовых файлов
оставлен явный CLI-флаг `-sandbox-allow-host-execution`; для вредоносных образцов
он не подходит.

## 4. Восстановить отчёт без VM

Если анализатор прервали или гостевая Windows уничтожена:

```powershell
go run ./pkg/cmd/sandbox-collector -recover '.\analysis_output\sandbox\remote-123456\events.jsonl' -output .\recovered
```

Создаётся новый отчёт; исходный журнал не меняется. Незавершённая последняя
строка игнорируется, повреждение полной строки вызывает ошибку. Незавершённый
сеанс отмечается `remote_capture.incomplete: true`. События не исполняются,
пути из журнала не используются для выбора файлов на хосте.

## Что покрывает этот режим

Используются штатные Windows API-хуки; они устанавливаются до возобновления
корневого процесса. Готовность перехватов и намерение запуска сохраняются на
хосте до `resume`. Пропуски установки хуков видны в отчёте. Захваченный материал
описывается в [документации криптоперехватов](SANDBOX_CRYPTO.ru.md).

Сейчас удалённый сборщик наблюдает **корневой процесс**. Frida child gating
останавливает дочерние процессы; сборщик завершает их и записывает пропуск
покрытия. Это меняет поведение образца и может помешать извлечению ключа,
если шифрование должно было выполняться в дочернем процессе. Инъекции в уже
работающие процессы, ядро и собственная криптография могут быть не видны.
Файловые/реестровые снимки, PCAP и kernel telemetry в этом режиме не собираются.

Лимиты приёма: 64 КиБ на событие, 64 МиБ журнала, 100 000 событий,
256 записей материала ключей. JSON содержит первые 512 API-вызовов; полная
принятая история находится в журнале. При ошибке/переполнении сбор прекращается
и результат помечается незавершённым. Heartbeat проверяет соединение с агентом.

При остановке сборщик пытается завершить удалённый процесс. При обрыве связи
подтвердить это невозможно: VM нужно остановить/откатить вручную. Записанные
на хосте ключи при этом остаются. Для реальной расшифровки файлов ещё нужны
соответствующие алгоритм, режим, IV/nonce/tag и формат шифротекста.

## Проверка без вирусов

```powershell
go test ./pkg/internal/sandbox ./pkg/cmd/analyzer -run 'TestRemote|TestRunBlocksHostExecution'
python -m unittest discover -s scripts -p test_remote_frida.py
```

Тесты проверяют запись ключа до завершения сеанса, восстановление после обрыва,
ограничения входных событий, отказ от запуска на хосте и порядок установки
перехватов/подтверждения/возобновления через имитацию Frida. Реальная VM и реальные
вредоносные файлы в этих тестах не запускаются.
