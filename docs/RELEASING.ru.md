# Выпуск релизов

[English](RELEASING.md)

Релизы полностью автоматизированы через [`.github/workflows/release.yml`](../.github/workflows/release.yml).

Перед тегом выполните [актуальный чек-лист](RELEASE_CHECKLIST.md).
Изменения тестов, проверок и настроек CI не требуют повышения версии.
Изменение VERSION не заменяет существующие теги. В этом репозитории уже занят
исторический тег `beta.1`; проверяйте выбранный тег при подготовке публикации.

## Как нарезать релиз

Проверьте изменения, выполните чек-лист и закоммитьте подготовленные файлы.
Меняйте версию через `bump_version.py` только при намеренной подготовке нового
выпуска. Для текущего VERSION проверьте предлагаемый тег:

```bash
release_tag="v$(cat VERSION)"
git diff
git tag --list "$release_tag"
```

Поиск тега должен вернуть пустой результат. После коммита убедитесь, что рабочее
дерево чистое и подпись настроена, затем создайте и отправьте совпадающий тег:

```bash
git status --short
git tag "$release_tag"
git push origin "$release_tag"
```

В новом репозитории из экспорта исходников проверьте его собственные теги перед
выбором номера. Не перезаписывайте исторический тег принудительно.

Дальше workflow:

1. Кросс-компилирует чисто-Go **core**-анализатор (один исполняемый файл `analyzer`;
   для REST-сервера используй `analyzer --api`) под Linux, Windows и macOS,
   на `amd64` и `arm64` (CGO выключен).
2. Пакует каждую цель в `.tar.gz` (`.zip` на Windows) вместе с
   `LICENSE`, `COPYING`, `NOTICE.txt`, лицензиями сторонних компонентов,
   инструкциями EN/RU, демо, примером native APK и `minisign.pub`.
3. Скачивает готовые `amd64`-архивы на Linux (`ubuntu-latest`), Windows
   (`windows-latest`) и macOS (`macos-15-intel`) и проверяет их после распаковки
   без пересборки. Ошибка на любой платформе останавливает публикацию.
4. Генерирует `SHA256SUMS.txt` по всем архивам.
5. Подписывает `SHA256SUMS.txt` через minisign и проверяет подпись по публичному
   ключу репозитория. Отсутствующий или несовпадающий ключ останавливает публикацию.
6. Публикует GitHub Release с заметками из `docs/RELEASE_NOTES.md` и всеми артефактами.

> Готовые артефакты — это только **core**-сборка. Опциональные нативные движки
> (OmniSec/Zig/GNN) в виде бинарников не распространяются — собирай их сам по
> [docs/BUILD.ru.md](BUILD.ru.md).

## Настройка подписи (один раз)

Подпись публичного релиза обязательна. Локальная сборка и проверка архивов
работают без ключа подписи. Настройте подпись до отправки релизного тега:

1. Сгенерируй minisign-ключ **без пароля** (CI не сможет его ввести):
   ```bash
   minisign -G -W -p minisign.pub -s minisign.key
   ```
   В репозитории уже есть `minisign.pub`; если генерируешь новый ключ —
   замени его на свой и закоммить.
2. Добавь **приватный** ключ как секрет репозитория с именем `MINISIGN_SECRET_KEY`
   (Settings → Secrets and variables → Actions). Вставь полное содержимое
   `minisign.key`.
3. Храни `minisign.key` офлайн. Никогда не коммить его.

## Проверка загрузки (для пользователей)

```bash
# Проверить подпись файла контрольных сумм по вложенному публичному ключу
minisign -Vm SHA256SUMS.txt -p minisign.pub

# Затем убедиться, что хеш твоего архива есть в списке
sha256sum -c SHA256SUMS.txt --ignore-missing
```


Core-архивы собирает `scripts/release.py`. Smoke-задача общего `core.yml` сейчас
работает только на Linux; проверки трёх ОС выполняет выпускной workflow по тегу.
ARM64-цели кросс-компилируются, но их запуск не проверяется. Результаты сохраняются
в артефактах `release-smoke-evidence-*`.
Пока квота Actions недоступна, записывайте локальные результаты и непроверенные
платформы: кросс-компиляция не подтверждает запуск архива. После возврата квоты
выполните все выпускные проверки перед публикацией. Предварительные выпуски
помечаются как prerelease и используют `docs/RELEASE_NOTES.md`.
