# Нативный декодер и сборщик APK

1 ноября 2026: удалены внешние JAR smali/baksmali, ANTLR и их зависимости,
обнаружение JAR, Java-backend декодирования и Java-fallback сборки DEX.
`--build` использует собственный Go-парсер Smali и ассемблер DEX.
`--smali-api` и `--smali-jobs` настраивают нативный сборщик.
Флаги путей к JAR, настройки JVM и форматирования baksmali удалены.
`auto` и `native` используют встроенный декодер; неподдерживаемые конструкции
возвращают ошибку сборки без запуска внешнего ассемблера.

Ниже сохранена история предыдущих обновлений. Описания встроенных JAR/JRE,
baksmali-backend и их флагов относятся к старой реализации.

# Декодер/сборщик APK: исправления и встроенные инструменты

Дата: 29 сентября 2026. Сводный патч `mega-analyzer-all-v1-v2-v3.patch` (объединяет три предыдущих патча; применяется к чистому архиву `Mega-Analyzer.zip`).

Проверено на реальных приложениях (NewPipe, F-Droid) на Linux: декод, сборка, сравнение с apktool 3.0.3. Windows/macOS-сборки только компилировались, на реальной Windows не запускались.

## Исправления

| Участок | Проблема | Изменение |
| --- | --- | --- |
| `smali_tree_validator.go` | Ложное срабатывание: строки-константы, содержащие `-switch`, считались опкодами ветвления. | Новый `isBranchOpcode`, строковые литералы вырезаются перед разбором. |
| `rebuilder.go` | Пользовательский `-smali-jar` отбрасывался (пустой `JavaBinary` заменял всю конфигурацию). | Недостающие поля добираются из авто-конфигурации, явные значения сохраняются. |
| Быстрая сборка | «Быстрая» сборка на самом деле просто упаковывала исходный dex; правки smali не попадали в APK. | В конце `decode` сохраняется снимок хэшей smali-каталогов (`.mega-analyzer-build-cache.json`). Smali не менялся — используется исходный dex без Java. Менялся — dex собирается заново (только изменённые dex), без ассемблера — явная ошибка. Нет снимка — предупреждение, старое поведение. |
| Сжатие | `dex` и `.so` хранились без сжатия (APK 20+ МБ). | `dex`/`so` сжимаются; `so` хранится без сжатия только при `doNotCompress` в мета-файле или `extractNativeLibs=false`. Режим по умолчанию `fast` → `balanced`. Проверка сжатия больше не требует STORE для dex/so. |
| `axml/exporter.go` | `&apos;` в строках (aapt2 требует `\'`), файл `pluralss.xml` вместо `plurals.xml`. | Общая функция `escapeAndroidString`, исправлено имя файла. Экспортированные `res/values*/*.xml` не упаковываются повторно, если в дереве есть `resources.arsc`. |
| `aapt2` | В коде был жёстко прописан путь разработчика `F:/PROJECTS/tinyapk-lab/...`; aapt2 запускался даже для нативно декодированных деревьев. | Путь удалён, добавлен поиск через локатор, для нативно декодированных деревьев aapt2 пропускается. |
| Язык | Часть пользовательских сообщений и путь `.\bin\analyzer.exe` были зашиты по-русски/под Windows. | Сообщения в `cmd/analyzer`, `ml`, `privserver` переведены на английский, `selfCmd()` определяет путь к исполняемому файлу. Русские значения tier (`имба/нормально/мусор`) оставлены: они сохраняются в данных. |

## Встроенные инструменты (новое)

- В бинарник встраиваются (`go:embed`): `mega-smali-tools.jar` (smali + baksmali 3.0.9, 4,9 МБ) и `aapt2` для Windows/Linux/macOS. При первом использовании распаковываются в кэш пользователя (`MEGA_TOOLS_DIR` переопределяет путь).
- Минимальная JRE (jlink: `java.base`, `java.xml`, `java.logging`; 23–26 МБ на ОС) встраивается только с тегом `-tags embedjre`. Архивы собирает `scripts/make-jre.sh`. `-tags noembed` отключает встраивание.
- Порядок поиска каждого инструмента: флаг → `MEGA_*` → `tools/`, `bin/`, `jre/` рядом с exe → системная Java (`JAVA_HOME`, PATH, Android Studio JBR и т. п.) → встроенная копия. `MEGA_EMBEDDED_JRE_ONLY=1` принудительно берёт встроенную JRE.
- Новый флаг `-tools-info` показывает, что найдено и откуда. Подпись через `apksigner` тоже использует найденную Java.
- `-smali-jobs` по умолчанию теперь `NumCPU` (было `NumCPU/2`).
- Режим `-dex-backend auto` при доступных jar и Java берёт baksmali (пересобираемый smali), поэтому декод медленнее нативного (NewPipe ~6 с против ~1 с). Для быстрого просмотра без правок: `-dex-backend native`.

## Измерения (Linux, 2 CPU)

| Сценарий | apktool 3.0.3 | Mega-Analyzer |
| --- | --- | --- |
| Декод NewPipe | 6,8–7,4 с | 1,1 с (native), 6,3 с (baksmali) |
| Декод F-Droid | 9,4 с | 2,1–2,7 с (native), 11,3 с (baksmali) |
| Сборка без правок smali | 15 с / 19 с | 1,2–1,6 с |
| Сборка с правкой smali (встроенная JRE, без Java в PATH) | — | NewPipe 18,6 с, F-Droid 19,8 с |

## Известные ограничения

- Нативный DEX→Smali теряет метки, `.line` и аннотации: его вывод нельзя пересобрать. Для правок используйте baksmali (режим auto).
- `values-es-r419` экспортируется без `b+es+419`; экспорт `attr`/`id`/`drawable`/`styleable` неполный.
- Встроенная Windows-JRE собрана кросс-jlink и на реальной Windows не проверялась.
- Правки этого выпуска: тесты `apkloader`, `cmd/analyzer`, `ml`, `privserver` проходят на Linux. Полный `go test ./...` не запускался.

# ML-патчер v3: корректность стратегий и границы применимости

Дата: 25 сентября 2026. `PlannerVersion = planner/v3`. Схема артефакта: `2.1.0`.

Это продолжение предыдущего изменения (`planner/v2`), а не новая обученная модель. Исправлены конкретные ошибки генерации и учёта результатов. Рост эффективности на реальных приложениях не измерялся; APK не запускался и не модифицировался. Go-компиляция и Go-тесты пока не выполнены из-за отсутствующего toolchain.

## Что нового относительно v2

| Участок | Проблема | Изменение |
| --- | --- | --- |
| Native/abstract | Общий путь планирования мог принимать декларацию без Smali-реализации. | Проверка флагов из `MethodHeader`, объявления в `RawBody` и `IsAbstract`. `native` направляется на отдельный native-анализ, `abstract` отклоняется. Проверки действуют в общих request/assessment/generator-входах, включая legacy `Generate`. |
| Отсутствующее тело | Планировщик мог пытаться синтезировать правку по одной сигнатуре. | `PlanPatch` возвращает `no_concrete_method_body`. Annotation/payload-данные не считаются исполняемыми инструкциями. Старый legacy API для signature-only preview не удалён. |
| Контракт метода | Совпадение имени и дескриптора не запрещало изменение `static`, видимости или синхронизации. | Сравнение множеств флагов объявления с сохранением числа их вхождений; порядок и комментарии не влияют. Отказ при разных флагах между исходным header/body, нескольких объявлениях в патче и generated native/abstract. |
| Определение регистра | Предыдущая строка `const` считалась источником возврата даже при входе по метке/числовому переходу непосредственно в `return`. | Предыдущая инструкция определяется внутри прямолинейного участка. На границах блока доказательство обрывается; известные числовые цели учитываются по DEX code units. Неразбираемые числовые раскладки дают отказ от оптимизации. |
| Единственная константа | Единственное текстовое определение считалось доминирующим, даже если его можно обойти. | Дополнительное консервативное доказательство: определение в начальном прямолинейном участке до возврата, без предшествующего перехода/выхода/метки и без layout hazards. Безопасные single-def оптимизации сохраняются; полноценный dominator-анализ всех видов Smali не заявляется. |
| Wide/object | Поиск константы назад на шесть строк перескакивал перезапись регистра или границу блока. | Для size-neutral swap используется только непосредственный исполняемый предшественник в том же прямолинейном участке. Иначе вставка через существующий движок либо честно непокрытый сайт. |
| Object opcode/type | Замена `const-string/jumbo` на `const-string` меняла ширину; String/Boolean swap не сверял тип контракта. | Сохраняется исходный string opcode, в том числе jumbo; String/CharSequence и boxed Boolean проверяются раздельно. |
| Числовые переходы | Концевой комментарий мешал обнаружению/пересчёту offset. | В затронутых местах используется `smaliCodeLine`. При переписывании перехода его концевой комментарий может быть удалён; исполняемая часть пересчитывается. |
| Частичность | Выбор кандидата зависел от слов `left unforced` в описании. | Добавлен `ReturnSiteCoverage{Opcode, TotalSites, HandledSites}`. Семь встроенных семейств инъекций (включая два boolean-входа) заполняют структуру. Планировщик проверяет диапазоны и соответствие числа сайтов исходному телу. |
| Применение частичного патча | Частичный результат мог иметь разрешение автоматической записи. | Такой артефакт получает `CanWrite=false`, `Safe=false`, уровень review либо сохраняет blocked. `GenerateWithMode` выставляет `needs_review`, не повышая существующий reject. Полный кандидат по-прежнему предпочтительнее частичного независимо от их приоритетов. |

`HandledSites` — отчёт генератора о покрытых возвратах, включая уже возвращавшие нужное значение. Это **не количество изменённых инструкций и не доказательство поведения на ART**. `ReturnCoverage=nil` означает старый/неизвестный формат: для сторонних стратегий оставлен совместимый разбор описания. Новое поле также сериализуется в `PatchArtifact`; автоматически доверять данным внешнего плагина нельзя.

`PreserveSideEffects` ещё не является сквозным доказанным контрактом. Этот выпуск исправляет перечисленные случаи неверного выбора определения регистра, но не доказывает сохранение всех побочных эффектов всех стратегий, корректность всех register aliases, обработчиков исключений и неизвестных opcode. Ограничения методов низкого уровня `strategy.Generate` не следует путать с общими входами планировщика: для единого набора проверок используйте `BuildChangeRequest` → `PlanPatch` или `GenerateWithMode`.

## Проверка предоставленного APK

Вложение `hill-climb-racing-1-14-0-es-en-android.md` действительно является ZIP/APK-контейнером. `hill-climb-racing-original.apk` — его побайтовая копия с корректным расширением, **не модифицированная сборка**. Подлинность подписи и соответствие версии имени файла не устанавливались.

В `classes.dex` найдены 2 198 классов и 14 629 определённых методов: 13 790 с code item, 26 native и 813 abstract. У всех 839 native/abstract-методов отсутствует DEX code item; противоречий этих access flags и code_off не обнаружено. Есть `libgame.so` для armeabi, armeabi-v7a и x86. Native-логика не становится доступной Smali-генератору только из-за наличия Java/JNI-обёртки.

Подробности и SHA-256 находятся в `docs/APK_REPORT.md` и `docs/validation/hill-climb-racing-static-profile.json`. Добавлен read-only инструмент `scripts/apk_static_profile.py` без внешних Python-зависимостей. Он не запускает APK, не извлекает файлы на диск и не выполняет ML-планировщик. JSON инвентаризации **не является** результатом `go test` или экспериментом успешности патчинга.

## Как использовать поставку

`Mega-Analyzer-ML-v3.zip` содержит **полный обновлённый проект**, `CHANGES.md`, `APK_REPORT.md`, тесты, JSON/логи и оба `.patch`. В ZIP не включены исходный APK, git-база и Python cache.

`ML-patcher-v3.patch` — накопительный патч **поверх исходного** `Mega-Analyzer-original.zip` (SHA-256 `e712f1fa71668d877354bd5eb2668250cdd9a11c62260c834c7b52fa8b813791`). Включает предыдущие изменения v2. `ML-patcher-v2-to-v3.patch` — только продолжение **поверх предыдущего** `Mega-Analyzer-ML-improved.zip` из этой беседы. Ни один патч не нужно применять к готовому ZIP v3. Патчи не включают сами себя; старый вложенный patch в ZIP v2 может остаться как исторический файл и не влияет на исходники.

Из корня соответствующей распаковки:

````sh
git -c core.whitespace=cr-at-eol apply --check /path/to/ML-patcher-v3.patch
git -c core.whitespace=cr-at-eol apply /path/to/ML-patcher-v3.patch
````

Для базы v2 замените имя на `ML-patcher-v2-to-v3.patch`. После установки совместимого Go обязательно выполните:

````sh
go version
go test ./pkg/ml -run '^(TestPlannerV3|TestReturnPredecessor|TestPlannerSafety|TestOutcomeSafety|TestOverrideReturns_)' -count=1
go test ./pkg/ml/... -count=1
go test -race ./pkg/ml -run '^TestOutcomeSafety' -count=1
go vet ./pkg/ml/...
go test ./...
````

Проверьте форматирование изменённых `.go` штатным `gofmt`. Python-проверки воспроизводятся отдельно:

````sh
python -m unittest discover -s scripts -p test_apk_static_profile.py -v
python scripts/apk_static_profile.py /path/to/hill-climb-racing-original.apk --output /tmp/apk-profile.json
````

Описание предыдущего этапа сохранено в `docs/CHANGES-v2.md` как исторический документ. Его версия и имена файлов относятся к v2, а не к текущему выпуску.
