# smalirole — «что делает эта константа?» (Jev-style, офлайн)

Отвечает на один типизированный вопрос про Smali: **какую роль играет литерал** (`0xFFFFFFFF`, `0x7f0b001c`, `250` …).
Ответ всегда из фиксированной схемы (как enum у Jev): ни одного выдуманного поля. Для каждой роли выдаётся вероятность, затем следы в коде и сгенерированное объяснение.
CPU-only, только stdlib Go, без LLM и сети. Модель весит ~0,4 МБ.

```powershell
.\bin\decision-ai.exe role -input examples\role-request.json            # модель подхватывается из models\smalirole-model.json
.\bin\smali-role.exe -file Method.smali -line 3 -text                    # только текст
.\bin\smali-role.exe dataset -root decoded_apps -out data.jsonl          # корпус из apktool-выходов (одна папка = одно приложение)
.\bin\smali-role.exe train -data data.jsonl -out models\smalirole-model.json
```
API: `POST /api/role` (тот же токен, что `/api/ask`), тело — `{"code": "...", "line": 3, "threshold": 0.6}`.

## Схема ответа
`bitmask, flag_bit, sentinel, color_argb, layout_param, boolean, limit_threshold, counter_step, duration_ms, resource_id, index_or_size, api_constant, unknown`.
Если уверенность ниже порога (по умолчанию 0.6), ответ — `unknown` (abstain). Если биты читаются как float (`add-float`, параметр `F`), ответ — `unknown` + `float_value` (например `0x41800000 = 16.0f`).

## Как устроено
1. **Парсер и CFG**: метки, `goto/if/switch`, `{v0 .. v5}`, wide-параметры (J/D занимают 2 регистра), payload-блоки пропускаются.
2. **Def-use трассировка**: от `const` по всем путям, с алиасами `move`, со сбросом при перезаписи регистра и на один уровень внутрь методов приложения (в режиме корпуса).
3. **Сигналы**: побитовые/арифметические операции, сравнения (с чем сравнивают: результат вызова, поле, параметр, длина массива), тип параметра/поля в сигнатуре, имя вызываемого API, форма литерала (−1, 0x7f…, степень двойки, старший байт…), контекст метода.
4. **Модель**: мультиномиальная логистическая регрессия (AdaGrad, L2, веса классов freq^-0.75), температура подобрана на отдельных приложениях → проценты откалиброваны.
5. **Объяснение**: текст собирается из найденных фактов, а не генерируется свободно, поэтому не может утверждать то, чего трассировка не видела.

## Данные и честность метрик
Корпус — open-source APK с F-Droid (лицензии GPL/Apache/MIT/BSD), декомпиляция apktool; библиотеки (`androidx`, `kotlin`, `com/google` …) исключены, дубли методов удалены.
Метки — **weak supervision**: `resource_id` — по `res/values/public.xml` (истина), остальное — по сильным типизированным приёмникам (`setTextColor` → цвет, параметр `Z` → boolean, `new-array` → размер, `if-eq` с −1 → маркер …).
Разделение по приложениям 60/20/20 (одно приложение целиком в одной части).

- `test_masked_*` — приёмник, давший метку, **спрятан**: модель угадывает роль по остальному контексту. Это честная метрика обобщения.
- `test_full_context` — всё видно; это согласие с правилами разметки, а не с человеком.

Метрики текущей модели лежат в `models/smalirole-metrics.json`.

## Ограничения
- Метки не проверены человеком; при выборочной проверке встречается шум (например, `0` в `setDuration`).
- Межпроцедурно — только один уровень и только в режиме корпуса; поля между методами не отслеживаются.
- `const-wide` (long/double) пока не разбирается; float определяется только по использованию.
- Редкие роли (`duration_ms`, `flag_bit`) учатся хуже: мало примеров.

# patch-effect — что сделает патч, шанс что сработает, сколько работы

```powershell
.\bin\decision-ai.exe patch-effect -input examples\patch-effect-request.json
```
API: `POST /api/patch-effect`. Тело: `code`, `line`, `expected`, `replacement`, `app_owned`, `library`, `server_dependency`, `target`.

Ответ:
- `what_it_does` — роль литерала (smalirole) + направление изменения («поднимает лимит 10 → 30», «включает флаг», «сокращает задержку 5 с → 500 мс»). Текст собран из трассировки, без генерации.
- `clamps` / `effective_value` — найденные ограничители после литерала (`if-le/lt/ge/gt` + `move`, `Math.min/max`, Kotlin `coerceAtMost/AtLeast`) и значение, которое получится на самом деле.
- `success` — вероятность, что патч даст задуманный эффект, из именованных факторов (роль понята, значение используется, float/int, сервер, ограничитель, тип изменения, механика рерайта) + жёсткие потолки: не выше 90% без сборки/теста, не выше 50% при серверной зависимости, не выше 40% если ограничитель срезает значение. `band`: low / partial / medium / high.
- `effort` — сложность (trivial / low / medium / high), диапазон минут и причины (сколько мест использования, межпроцедурность, сервер, ограничитель, нужен ли другой opcode).
- `plan` — сам рерайт: 32-битные `const*` через `engine.PlanPatch`, `const-wide`, `/16` и `/32` (long, например задержки) — свой планировщик с выбором самого узкого opcode. `can_apply` всегда `false`.

**Важно:** `success.probability` — структурная оценка, она НЕ откалибрована на реальных исходах патчей (такого датасета нет). Это не «шанс, что приложение заработает», а «насколько код подтверждает, что литерал влияет на задуманное». Подтверждают только сборка, тест и человек.

# v0.4 — аудит меток, поля, связка роль → план патча

**Аудит таймаутов.** Вручную проверены метки `duration_ms`: раунд 1 — 55/60 верных (91,7 %); ошибки (sentinel −1, `what` у `sendEmptyMessageDelayed(IJ)`, `getDuration(I)`, `setTimeInMillis`, ID ресурса в `setDuration`, конверсии `TimeUnit.toMillis`) закрыты правилами. Раунд 2 на новой выборке — 40/40 (нижняя граница 95 % ДИ ≈ 0,91). Вызовы с `TimeUnit` помечаются `time_unit_arg: true` — роль «длительность», но единица не мс. Это число (0,91) подмешивается к вероятности, когда значение доходит до типизированного timing-API: модель редко видела такие случаи через поля/вызовы.

**Поля.** `iput/sput` → все `iget/sget` поля в приложении (до 8 мест), в том числе `const-wide` → `sput-wide` в `<clinit>` → `postDelayed` в другом классе. Для этого нужен индекс приложения: `-app <папка apktool>` (только CLI, не HTTP). Класс метода определяется автоматически (`-class` — вручную).

**Перезапись поля.** Если литерал кладётся в поле, а поле пишется ещё где-то, отчёт выдаёт `field_overwrites`, фактор успеха `field_overwritten` и вердикт `review`. Самый частый случай — значение по умолчанию в `<init>`/`<clinit>`, которое затирает `onCreate` или сеттер: тогда шанс успеха ≤ 45 %. На корпусе так устроено 79 % литералов, записанных в поле, поэтому общий штраф мягкий (−0,8), а за значение по умолчанию строже (−1,6).

**Связка с `decision-ai analyze`.** `PlanPatch` теперь сам спрашивает роль (`engine.PatchAdvisor` ← `patcheffect.Advisor`). В отчёте появляется блок `advice` (роль, %, что делает патч, шанс, трудозатраты, effective value, вердикт). `plan.explanation` вместо «назначение не установлено» объясняет смысл. Advice может только ужесточить решение: `blocked`, если float, ограничитель возвращает исходное значение или значение не читается; `review`, если роль неизвестна, ограничитель срезает значение, поле перезаписывается, риск типа repoint/sentinel или шанс низкий. Если `PlanPatch` не умеет менять `const-wide`, используется широкий план из patcheffect.

```
decision-ai analyze -input req.json -app path/to/apktool_out
decision-ai patch-effect -input pe.json -app path/to/apktool_out
smali-role -file M.smali -line 7 -model models/smalirole-model.json -app path/to/apktool_out
```
