# DecisionAI v0.3 · модуль для Mega-Analyzer

**Текстовый режим с STATE / QUESTION / TRUE WHEN / FALSE WHEN:** см. `TEXT-MODE.ru.md`. Этот файл ниже описывает сохранённый структурированный режим v0.1. Накопительный .patch содержит обе версии; готовый EXE собирается через BUILD-WINDOWS.cmd.


Рабочий CPU-only MVP: фильтрация и ранжирование находок, декларативные вопросы по state, две независимые оценки, обучение небольшой модели, локальная Input Form и проверяемый план изменения одного литерала Smali.

**Windows 10 x64 / i5-3340 / 10 ГБ ОЗУ:** сборка `bin/decision-ai.exe` после BUILD-WINDOWS.cmd использует базовый набор инструкций x86-64 (GOAMD64=v1), без AVX2, CUDA, Python и внешнего сервера. GPU не используется. Сборка проверена кросс-компиляцией; выполнение EXE на реальной Windows и скорость на компьютере пользователя не проверены.

## Быстрый старт — PowerShell

Открой терминал в этой папке:

```powershell
.\bin\decision-ai.exe serve
```

Открой **http://127.0.0.1:7475** в браузере. Выбирай Input Form или JSON. В примере меняется литерал 10 → 20; назначение не считается доказанным. Ctrl+C останавливает сервер.

Без сервера:

```powershell
.\bin\decision-ai.exe analyze -input examples\request.json > report.json
.\bin\decision-ai.exe batch -input examples\states.json > reports.json
.\bin\decision-ai.exe test -input examples\tests.json
.\bin\decision-ai.exe analyze -input examples\request.json -threshold 0.70
```

`analyze`: один Request. `batch`: JSON-массив Request. `test`: сценарии с ожидаемыми ответами, решением, проверкой и наличием плана. При несовпадении тестов код завершения 1. Данные не отправляются в сеть. Для результата доступны скачать JSON и точный diff. Форма не сохраняет введённые данные после перезапуска страницы.

## State / Question / True when / False when

```json
{
  "state": {"tests": {"passed": true}, "local_only": true},
  "questions": [{
    "question": "Подтверждён ли локальный тест?",
    "true_when": [
      {"field": "tests.passed", "op": "eq", "value": true},
      {"field": "local_only", "op": "eq", "value": true}
    ],
    "false_when": [
      {"field": "tests.passed", "op": "eq", "value": false}
    ]
  }]
}
```

Это фрагмент Request, не полный файл для запуска. Полный файл — `examples/request.json`.

- Список условий внутри ветки объединяется **AND**.
- `true`: true_when выполнена и false_when не выполнена.
- `false`: false_when выполнена и true_when не выполнена.
- `unknown`: данных не хватает, типы не подходят, одна ветка не задана или ни одна не выполнена.
- `conflict`: обе ветки выполнены; кандидат блокируется.
- Поддерживаются `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `exists`.
- `field` — путь к вложенному объекту через точку. Индексы массивов не поддерживаются.
- Для `exists` передавай boolean; для `in` — массив; для сравнений порядка — JSON-число. Строка `"10"` не число.
- `exists:true` считает присутствующий null существующим значением.
- Вопросы описывают входной state. **State сообщает пользователь/интеграция: модуль не запускал эти тесты и не удостоверял их результаты.** Ответ false не означает запрет любого патча: смысл вопроса произвольный. unknown запрещает переход к candidate_for_review; conflict блокирует план.
- Условия — данные, а не код: нет eval, shell или выполнения выражений.

## Threshold

```json
"threshold": {"finding": 0.65, "patch": 0.85}
```

Диапазон 0..1 включительно. Граница включена (`score >= threshold`). CLI `-threshold` переопределяет оба порога. Отсутствующий объект использует defaults 0.65/0.85; если объект указан, в нём указывай оба поля (нулевое значение означает нулевой порог).

Порог **не превращает эвристический score в вероятность**. Находка ниже порога сохраняется как low_priority. Патч выше порога — только candidate_for_review, не автоодобрение и не запись на диск. Порог не отменяет конфликты, проверки принадлежности или невалидный исходник.

## Как устроены оценки

Две разные задачи:

- `finding`: метка 1 означает подтверждённую релевантную находку, 0 — подтверждённый шум.
- `patch`: метка 1 означает подтверждённый нужный эффект конкретного класса кандидатов, 0 — отсутствие эффекта/неподходящий результат. Модель использует признаки метода и выбранного кандидата (относительная величина изменения, масштаб нового литерала, preflight, смена opcode), но **не доказывает семантику diff**. Поэтому это оценка похожести на прошлые случаи, не гарантия успеха выбранной замены. Для обучения patch каждый пример обязан содержать конкретный patch Request.

Без model JSON используются явно обозначенные `heuristic_score`. Они не обучены и не являются вероятностями. Объяснения показывают вклад каждого признака.

Обучение: логистическая регрессия на 15 ограниченных признаках (числа инструкций, вызовов, ветвлений, констант, return, бюджет регистров, заявленные evidence/ownership/library/server_dependency, наличие патча, относительный delta, масштаб replacement, preflight и смена opcode). Это не LLM и не полноценный семантический классификатор. Имена переменных сами по себе не доказывают смысл.

Разделение по app/project `group`: 60% групп fit, 20% calibration, 20% test. Platt-калибровка выполняется только на calibration. Минимум 10 групп, 40 train, 20 calibration, 20 test и 5 примеров каждого класса в каждой части. `test_brier` и `test_accuracy_at_0_5` относятся только к заданному корпусу, не к любому приложению. После обучения contributions — слагаемые логита, не причинные объяснения.

**В поставке нет модели с заявленной реальной точностью.** Синтетический корпус ниже нужен исключительно для проверки механики обучения:

```powershell
.\bin\decision-ai.exe train -input examples\synthetic-training.json -output demo-finding-model.json
.\bin\decision-ai.exe analyze -input examples\request.json -finding-model demo-finding-model.json
.\bin\decision-ai.exe serve -finding-model demo-finding-model.json
```

Для настоящей модели собери Dataset по примеру synthetic-training.json, укажи правильный target, группируй одно приложение/проект в одну группу. Не размазывай один проект по нескольким groups и удали дубликаты между группами. Отметка «принял патч» — не метка успешного runtime. Ownership/evidence — входные метаданные, не независимо проверенные факты.

Для второго файла:

```powershell
.\bin\decision-ai.exe train -input my-patch-training.json -output patch-model.json
.\bin\decision-ai.exe serve -finding-model finding-model.json -patch-model patch-model.json
```

Автоматического online-learning и доверия своим предсказаниям нет. Добавляй подтверждённые данные и запускай явное переобучение. Модель хранится в обычном версионированном JSON. Загружать model JSON стоит только из доверенного источника: метаданные качества файла не имеют цифрового удостоверения.

## Планировщик изменений

Поддерживается **одна явно выбранная строка** с `const/4`, `const/16` или `const` и signed int32. Линия нумеруется с 1, включая .method/.registers. `expected` защищает от устаревшего литерала. Генератор подбирает подходящий opcode и учитывает физический регистр pN. Не меняет бюджет регистров.

План создаётся только при `meta.app_owned:true`, `meta.library:false`, scope `defensive` или `test_fixture`. Scope `audit` только диагностический. Принадлежность заявляет пользователь; для реальной интеграции проверяй её по проекту.

В результате: полный исходный/изменённый код, SHA-256, построчный diff, before/after/delta, процент при ненулевом before и текст объяснения. Для отрицательного before процент — арифметика, а не утверждение о росте поведения. `target` обозначается как заявленная пользователем цель, не как доказанный dataflow.

`validation:preflight_pass` означает лишь частичные проверки: один полный метод, .registers/.locals, параметры (this и wide), границы используемых регистров, поддержанные const-операнды. **Это НЕ полный парсер Smali, CFG/dataflow, проверка всех opcode/типов/ветвлений, сборка APK или Dalvik verifier.** Абстрактные/native методы и целые .smali-файлы с несколькими методами пока не поддержаны.

`build:not_run`, `runtime:not_run`, `can_apply:false` всегда честно отражают возможности этой версии. Приложение не выполняет подозрительные APK и не применяет изменения автоматически. Для применения в собственном приложении сначала проверь актуальный hash, покажи diff, используй полный валидатор/сборку исходного проекта, резервную копию и тесты поведения. Автоматического apply/undo здесь нет: исходные файлы вообще не меняются.

## Подключение к Mega-Analyzer

Это отдельный add-on в `tools/decision-ai`, **не замена основного анализатора и не автоматически подключённый фильтр**. Существующий код Mega-Analyzer сохранён.

Для JSONExport из `pkg/ml/exporter_json.go`:

```powershell
.\bin\decision-ai.exe import-analyzer -input ..\..\patches.json > imported-requests.json
.\bin\decision-ai.exe batch -input imported-requests.json > decisions.json
```

Если этот путь не подходит, передай фактический путь к экспорту. Импортируется `schema_version` + массив `patches`, из каждого берётся `original_code`, ID и метаданные. Confidence, apply_safe и предложенный patched_code **не считаются разрешением/вероятностью и не применяются**. Импорт по умолчанию scope audit, ownership неизвестна, evidence пустой. Сигналы доверенного анализатора надо добавить явно. Экспорт с пустым/неполным original_code требует адаптера к полному методу; пакет сообщает ошибку, а не притворяется корректным.

Можно импортировать пакет `github.com/mega-analyzer/decisionai/engine` через локальную replace-директиву, но основной go.mod не изменён. Интеграция CLI через JSON не требует менять зависимости основного проекта.

## Тесты и сборка из исходников

Для add-on достаточно Go 1.22+; зависимости только stdlib. Версия Go основного Mega-Analyzer из go.mod остаётся без изменений и здесь не проверялась.

```powershell
go test ./... -count=1 -cover
go test -race ./...
go vet ./...
go test ./engine -run '^$' -fuzz FuzzSmaliNoPanic -fuzztime=3s -parallel=2
$env:CGO_ENABLED="0"; $env:GOAMD64="v1"
go build -trimpath -ldflags="-s -w" -o bin\decision-ai.exe ./cmd/decision-ai
```

Тесты включают true/false/unknown/conflict, операторы условий, границы Threshold, регистры p/v, wide-параметры, комментарии/строки, stale/no-op/out-of-range патчи, widening opcode, нулевые и отрицательные значения, scope, отсутствие auto-apply, JSON, обучение/сохранение, сценарии и HTTP-защиту.

Локальный сервер принимает только numeric loopback, проверяет Host и случайный токен сессии, ограничивает тело запроса и выставляет CSP. Не публикуй порт через reverse proxy. Обучение и загрузка файлов модели доступны через CLI, не через HTTP.
