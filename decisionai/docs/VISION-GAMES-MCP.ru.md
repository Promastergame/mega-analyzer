# Картинки, игры и MCP

Новые модули работают локально на CPU, без Ollama, GPU, сети и дополнительных весов.
Это специализированное зрение и поиск игровых ходов. Они не превращают текстовый
энкодер в универсальную мультимодальную модель.

## Что уже работает

Доступна [визуальная игровая](VISUAL-ARENA.ru.md): тетрис и шашки по PNG, ручная игра и автоплей.

Добавлены [тетрис и русские шашки](TETRIS-CHECKERS.ru.md): правила, форматы поля,
управление через MCP и отдельные измерения описаны по ссылке.

- PNG, JPEG, GIF: размеры, доли основных цветов, эвристический цветовой фильтр
  `sensitive` (skin, blood_dark, blood_bright, fluid_warm, fluid_yellow, fluid_white),
  распознавание контрастного поля крестиков-ноликов. GIF читается по первому кадру.
  Нет OCR и распознавания произвольных объектов на фотографиях. Скоры фильтра —
  НЕ вероятности (0..100, без калибровки); классы с конфликтом обычных цветов
  помечены `ambiguous` и имеют пониженный вес.
- Крестики-нолики: проверка состояния, полный поиск с alpha-beta отсечениями,
  выигрыш, блокировка угроз, защита от вилок. В тесте перебираются все возможные
  ответы противника; алгоритм не проигрывает при игре с пустого поля за X или O.
- Лабиринт: кратчайший путь с обходом стен и опасных клеток.
- MCP-клиент: stdio, согласование версии 2025-06-18, `tools/list` с пагинацией,
  чтение `inputSchema`, `tools/call`, JSON/text/image-результаты, ошибки и тайм-ауты.
  Проверяются обязательные поля, базовые типы и enum; полный JSON Schema проверяет
  сервер. Streamable HTTP, sampling и elicitation не реализованы.
- Игровой цикл: наблюдение → расчёт → один разрешённый инструмент → новое
  наблюдение. Ошибка, повтор состояния, конец игры или лимит шагов останавливают
  цикл. Неуспешные действия не повторяются автоматически.

## Ресурсный профиль

Целевые показатели пользователя: **<100 МБ RAM, <3% CPU всей машины, ответ ≤50 мс,
без GPU**. Это цели для измерения, не жёсткие гарантии ОС.

Команды `game`, `see`, `play`, `mcp-tools` не загружают текстовые веса. Они используют
один Go worker и мягкий лимит управляемой памяти 64 MiB. Для постоянного сервера:

```powershell
.\.tmp\dai-vision.exe serve -light
```

Лёгкий сервер прогревает декодирование и поиск до начала приёма запросов.
Время запуска процесса не входит в целевые 50 мс ответа.

**`-light` — отдельный игровой профиль.** Он не загружает прежний нейросетевой
текстовый ансамбль: обычные текстовые вопросы получают лексический fallback.
Обычный `serve` сохраняет прежний текстовый движок; его суммарная память и скорость
не ограничиваются показателями лёгкого профиля.

Одно изображение: до 1 MiB закодированных байтов и 1 048 576 пикселей.
Для большого скриншота сначала вырежьте игровое поле и уменьшите его размер.
Декодирование изображений выполняется последовательно. В игровом цикле по умолчанию
есть пауза 500 мс между действием и следующим наблюдением; это уменьшает среднюю
нагрузку, но не гарантирует отсутствие кратких пиков выше 3%. Ожидание не является
временем вычисления ответа. CPU и память браузера/MCP-сервера учитываются отдельно.

## Сборка и быстрый запуск

Из корня проекта (Go, без дополнительных библиотек):

```powershell
go build -o .tmp/dai-vision.exe ./cmd/dai
go build -o bin/game-mcp.exe ./tools/game-mcp
.\.tmp\dai-vision.exe game -input examples/games/tic-tac-toe.json
.\.tmp\dai-vision.exe game -input examples/games/maze.json
.\.tmp\dai-vision.exe see -image .tmp/game-budget/board.png
.\.tmp\dai-vision.exe play -input examples/games/play-maze.json
```

Последний пример запускает настоящий локальный MCP-процесс, проходит лабиринт
и печатает журнал состояний и действий. `board.png` создаётся скриптом измерений
`scripts/measure_game_budget.py`; для `see` можно указать свой файл.
В Linux/macOS используйте бинарник `bin/game-mcp` и замените путь в JSON-конфигурации.

## Формат игр

```json
{"game":"tic_tac_toe","board":["XX.","OO.","..."],"player":"X"}
```

Строки по три символа: `X`, `O`, `.`. X начинает. Действия `cell_0`…`cell_8`
нумеруются по строкам слева направо. `outcome` до конца партии описывает результат
при оптимальной игре обоих участников. При `terminal:true` ход отсутствует.

```json
{"game":"maze","grid":["S...#",".##..","...XG"]}
```

`S` — игрок, `G` — цель, `#` — стена, `X` — опасность, `.` — свободно,
`*` — игрок на цели. Действия: `up`, `right`, `down`, `left`.

## HTTP и обычный DecisionAI

`POST /v1/game` принимает состояние игры и возвращает рассчитанный ход.
Можно передать картинку вместо `board`/`grid`:

```json
{"game":"tic_tac_toe","image":{"mime_type":"image/png","data":"BASE64_BYTES"}}
```

`POST /v1/see` принимает `{"mime_type":"image/png","data":"BASE64_BYTES"}`
и возвращает размеры, sha256 картинки (`img_sha256`), цвета, скоры фильтра,
обводку боксов (`boxes: [{class,x,y,w,h,score}]`, координаты в пикселях
оригинала) и распознанное поле, если оно найдено.
Оба endpoint требуют `Content-Type: application/json` и Bearer token сервера.

## Разметка крови (RLHF)

Локальная страница `http://127.0.0.1:7480/collect` (только loopback):
загружаешь PNG/JPEG/GIF до 1 МБ и 1 048 576 пикселей, ИИ обводит найденное
боксами с классом (`blood_dark`, `skin`, …). Лайк — «да, кровь», дизлайк —
«нет»; лайков максимум 5 на картинку, дизлайков бесконечно. Кнопка
«Подсказать» — тянешь прямоугольник сам, это самый ценный голос.

Голоса копятся в JSONL (`-collect-feedback`, по умолчанию
`.tmp/collect-feedback.jsonl`) строкой
`{"img_sha256":"…","width":1400,"height":933,"box":{…},"vote":1,"src":"hint"}`.
По ним потом пересчитываются веса классов и калибровка скоров.
`GET /v1/collect/budget?sha=…` возвращает `{"likes":n,"max":5}` — остаток
бюджета подтверждений (ручные подсказки тоже считаются).
Свой объект размечается классом `custom:Название` (только `src:"hint"`,
аннотация, детектор не расширяет); подробности — в
[COLLECT-REDESIGN.ru.md](COLLECT-REDESIGN.ru.md).

`POST /v1/decide` также принимает `images:[{"mime_type":"image/png","data":"…"}]`.
Пиксельные наблюдения добавляются к текстовому состоянию; ответы требуют проверки.
Для точного расчёта хода по изображению используйте `/v1/game`, а не текстовый fallback.

Новый `task:"game_move"` в обычном `/v1/decide` направляет структурированное состояние
игры к игровому эксперту. Объявляйте ключи ходов в `criteria`. Если выбранного хода
нет в вариантах или состояние некорректно, ответ помечается `abstained:true`,
`route:"human"` — выполнять его нельзя.

## Своя игра через MCP

Возьмите `examples/games/play-maze.json`. В `server.command` укажите исполняемый
файл MCP-сервера, в `args` — отдельные аргументы, в `cwd` — рабочую папку при
необходимости. Команда запускается напрямую, без shell. Конфиг должен быть вашим,
не текстом, полученным от игры или модели.

`observe` по умолчанию должен возвращать картинку. Для старых адаптеров с
`structuredContent` или JSON-текстом явно задайте `observation_mode:"structured"`. `actions` сопоставляет логические ходы с реальными именами инструментов
и точными аргументами. Так подключаются и локальные, и браузерные игры; для конкретного
сайта нужен MCP-сервер с подходящими инструментами и настроенные соответствия.
Автоматического понимания правил незнакомой игры здесь нет.

Для крестиков-ноликов картинка должна содержать ровный квадратный контрастный
3×3 grid, обычные X/O и однотонный фон. Для большого кадра задайте
`image_layout:{"left":100,"top":50,"width":300,"height":300}`.
Координаты относятся к исходному изображению; они не вычисляются по уменьшенной копии.

Для лабиринта дополнительно задайте `rows` и `columns` в `image_layout`.
Палитра сплошных клеток: белый — свободно, чёрный — стена, синий — игрок,
зелёный — цель, красный — опасность, жёлтый — игрок на цели.
Произвольные текстуры и спрайты такой распознаватель не поддерживает.

`player:"X"`/`"O"` позволяет остановиться на ходе противника.
`max_steps` ограничивает число действий (по умолчанию 32, максимум 256).
`min_step_interval_ms` задаёт паузу между действиями и наблюдениями (по умолчанию 500).
Лимит одного MCP-запроса — 30 секунд; весь CLI-сеанс — 15 минут; Ctrl+C прерывает его.

## Проверка

```powershell
go test ./games ./vision ./mcpclient ./gameagent ./cmd/dai ./experts ./s1
go test ./games ./vision -run '^$' -bench 'BenchmarkEmptyBoard|BenchmarkReadBoard' -benchmem
python scripts/measure_game_budget.py
```

Последний скрипт измеряет HTTP-ответ «PNG → распознать поле → выбрать ход», память
процесса Windows и средний CPU при двух запросах в секунду. Результат:
`.tmp/game-budget/report.json`. Он не измеряет потребление произвольной внешней игры.

### Контрольный замер 15.10.2026

Windows, Intel Core i5-3340, 4 логических CPU, `serve -light`, PNG 300×300,
24 запроса «картинка → ход» по HTTP при 2 запросах/с, после завершения тестов:

| Показатель | Результат |
| --- | --- |
| Первый запрос после готовности сервера | 16,9 мс |
| Медиана / p95 | 17,6 / 30,5 мс |
| Максимум в этом прогоне | 35,4 мс |
| Рабочая память / пик | 18,3 / 19,3 МБ |
| Private committed memory | 55,1 МБ |
| Средний CPU в трёх прогонах | 0–0,24% всей машины |

Нулевой CPU в коротком прогоне означает нагрузку ниже разрешения счётчика,
а не отсутствие вычислений. Во время параллельных тестов был выброс 84,2 мс.
Таким образом, обычный проверенный сценарий укладывается в бюджет, но жёсткий
предел 50 мс при любой загрузке ОС и мгновенный потолок 3% CPU не гарантируются.
Это также не замер старого текстового ансамбля, внешнего MCP-сервера или браузера.

Сохранённые результаты: `checks/game-budget.json`,
`checks/game-budget-with-tests.json`. До добавления прогрева первый запрос занимал
238,8 мс; теперь прогрев завершается до открытия серверного порта.
